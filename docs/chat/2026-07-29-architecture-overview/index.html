結論。02-architecture.md の Resident Mesh は、境界としてはコードにほぼそのまま入っている。crate 依存グラフに逆流はなく、yuukei-daihon は protocol にすら依存しない完全な葉、Tauri 型は apps/desktop/src-tauri の外に出ていない。AGENTS.md の Avoid に対する明確な違反は見つからなかった。

ただし現状は 「Resident Mesh の形をした単一プロセス」である。Resident Home は独立サーバーではなく Device Host が ResidentHome 構造体を Arc で抱える in-process 呼び出しで、protocol は型としては JSON 化可能だが、まだ一度もプロセス境界を越えていない。Cloud-Capable Layout は設計のみ。プロセス境界を実際に越えているのは Extension（process JSONL）だけで、そこが唯一の実証済みリモート化ポイントになっている。

01全体像 — 4つの責務と、その実体

ドキュメントの5コンポーネントが、実際にどのファイルとして存在しているか。括弧内は実測行数。

境界の実際： Surface ↔ Device Host は Tauri IPC で本当に切れている（型は packages/yuukei-protocol に ts-rs で自動生成）。Device Host ↔ Resident Home は crate 境界のみで、通信ではない。Resident Home ↔ Extension は stdin/stdout の JSONL で、ここだけが実プロセス境界。

02crate 依存グラフ — 逆流はない

読みどころ。 yuukei-daihon の依存は chumsky / miette / rand / chrono だけで、yuukei-protocol すら入っていない。AGENTS.md の「Resident Home を Daihon 内部型に依存させない」が、yuukei-world の DaihonAdapter trait による間接化として実際に成立している。Resident Home は Arc<dyn DaihonAdapter> しか知らない。

03イベント一巡 — 観測1件が声になるまで

ResidentHome::ingest_event から emit_command_for_event までの実処理順。crates/yuukei-resident-home/src/event_flow.rs がこの流れの本体。

  1. 観測 → RuntimeEventdevice-host: desktop_observation.rs / life_rhythm.rs / runtime.rs ウィンドウ・フォルダ・ダウンロード・アイドル・スリープ復帰・5分ごとの presence.life_tick・設定間隔（既定5分）の presence.talk_impulse。観測3種は既定OFF、タイトルとフルパスは記録せずカテゴリへ正規化する。
  2. 検証 → 追記 → snapshot 反映validate_runtime_event → event_log.append → apply_runtime_event_to_snapshot residentId 一致、RFC3339、World Pack が宣言した actor か、privacy.category 非空。まず記録し、それから解釈する。
  3. 選択肢の解決 / 解釈中のキュー退避resolve_pending_choice_event / defer_event_while_interpreting 「解釈」await 中は conversation.* だけを最大16件キューへ積み、溢れたら daihon.interpretation.queue.dropped を記録して捨てる（捨てたことも記録に残る）。
  4. Extension へ通知 → 提案イベントの取り込みnotify_extensions_event_appended 購読中の Extension が新しい RuntimeEvent を提案する。Resident Home が検証して log へ追記し、同じループの後段へ回す（最大 MAX_EXTENSION_EVENT_HOPS = 4 段）。
  5. 気分と衝動の調停maybe_evaluate_mood / moderate_talk_impulse_event presence.life_tick で mood.evaluate を呼び、結果は ext.yuukei-intelligence.mood.changed として内部イベント化。talkDesire が低ければ presence.talk_impulse を握り潰し、presence.talk_impulse.skipped を残す。
  6. 文脈の付与（enrich）enrich_event_for_daihon_dispatch actorLocation / actorPresence / aiConnected を注入。desktop.folder.opened なら直近7日の desktop.download.completed を引いて「最近の届きもの」を足す。台本が状態を問い合わせる代わりに、Home が答えを持って行く形。
  7. signal の許可判定world_pack.allows_signal_with_aliases Pack の signals.allow と Extension が寄贈した別名の合成テーブルに無ければ、ここで静かに終了。
  8. Daihon dispatchdaihon.dispatch_with_interpret → daihon.dispatch.result を記録 台本が動けば RuntimeCommand 列が返る。「解釈」に当たると Home 側のハンドラが dialogue.interpret capability を呼び、その間 3 のキューが効く。
  9. 台本が沈黙したときだけ LLMmaybe_generate_dialogue_fallback（dialogue.generate, 上限120字） AI は隙間を埋めるだけで、台本を置き換えないという 01-concept の方針が、この分岐一箇所に集約されている。provider が居なければ何も起きない。
  10. beforeCommandEmit フックapply_extensions_before_command_emit Extension が RuntimeCommand を変換できる唯一の点（ExtensionHookPoint は現在この1種のみ）。実行順は開発者の priority ではなく settings/extensions.json のユーザー設定。
  11. 発話予約 → 記録 → 配信 → TTSemit_command_for_event 健全な speech.synthesis provider が居れば speechPending: true を付け、command も event log へ追記してから broadcast で Surface へ。TTS は別タスクで走り、完了時に audio.play（実長つき）が吹き出しの寿命を延ばす。
この流れの一貫性： RuntimeEvent も RuntimeCommand も、Surface に届く前に必ず event log へ入る。記憶・気分・記録 UI はすべてこの log からの派生で、どの派生も消して作り直せる。04-event-log-and-memory.md の「canonical log が正、他は derived」が実装として守られている。

07目に付いた構造上の論点（提案ではなく観察）

1. Resident Home が「サーバー」になる日のコスト

現在 Device Host は ResidentHome を直接 await している。protocol 型は全て serde 可能で ts-rs export もされているので型の準備は済んでいるが、ingest_event が Vec<RuntimeCommand> を同期的に返す形になっているのが、リモート化したときに最初に効く箇所になる。broadcast 側（command stream）は既にストリーム形なので、そちらは素直に乗る。

2. hook point が1種類だけ

ExtensionHookPoint の variant は BeforeCommandEmit のみ。02 が挙げる onEventAppended と signalAliases は hook ではなく、それぞれ event 購読・manifest 宣言という別経路で実装されている。ドキュメントは3つを並列に列挙しているので、読み手が「3つの hook point がある」と誤読しうる。02 の Extension 節の書き方だけ揃える余地がある。

3. 大きくなっている実装ファイル

yuukei-world/src/lib.rs 3943行が単一ファイル（WorldPack 定義・検証・DaihonAdapter・シーン履歴が同居）、device-host/src/runtime.rs 1219行。後者は ROADMAP に分割候補として載っているが、前者は載っていない。境界としては正しい位置にあるので緊急ではない。

4. Windows 実機確認が M5 の残タスク

M2 の観測（IShellWindows によるフォルダ遭遇、EnumWindows によるウィンドウ地形）が「Windows 実機未検証」のまま ROADMAP に残っている一方、直近3コミットは Windows 固有の修正（タスクバー干渉、常時前面窓の除去、キャプション）で埋まっている。実装は進んだが ROADMAP のチェックが追いついていない状態に見える。
